qa-system skill-authoring handbook

A badly written skill can make the AI invent data, make results drift between runs, or break the checking gates of the whole system. This page is a 6-step process for adding or editing a skill while the system keeps running exactly as before.

Never edit by handDelegate to the QA Leader through the system-upgrade-governance process.
Approve first, act afterRead the analysis table and the list of affected files before allowing any edit.
Done means evidenceTests green, integrity check clean, two real runs giving the same result.

The whole process

1

Analyze first, edit no file yet

Tell the AI: Upgrade skill <name>: <what you want to change>. Run PHAN_TICH (analysis) mode first. The AI answers three questions in order and stops at the first one that is true:

Only changes how an existing skill works? (add a column, tighten a rule, change a format)Yes → C · edit in place
Is there already an agent that handles exactly this area?No → B · new agent
If this work is given to that agent, must it read another kind of file, write somewhere else, or take on another role?Yes → BNo → A · add a skill

It comes with the list of affected steps (npm run agent:check -- --impact <agent>). You read this table, and only then allow the work. Prefer A or C; build a new agent only when really needed, because the more agents there are, the harder it is for the QA Leader to coordinate.

2

Put content in the right place

This is the most common mistake. The same sentence put in the wrong place becomes something entirely different.

The content is…Put it inWhy
A rule every skill must follow, or a table used by 2 or more skillsqa-system/core/QA_STANDARD.mdA rule lives in one place only. The skill writes "per QA_STANDARD §4" and does not copy it
Values, messages, thresholds of one specific featureknowledge/features/<slug>.mdIf left in a skill, the AI treats it as truth for every feature
The method, parameters, output sample of this task onlyqa-system/qa-<agent>/skills/<name>.mdA skill is "how to do it"
Who the agent is, what it may do, whom it hands back toqa-system/qa-<agent>/AGENT.mdIdentity and boundaries

Editing QA_STANDARD.md changes the rules of the whole system, so a human must decide; do not let the AI do it on its own.

3

Write the skill from the existing template

Always start from qa-system/templates/skills/ten-skill.md. A standard skill has all of the following parts. (The template's section headings such as Mục đích = Purpose, Đầu vào = Inputs, KHÔNG được = MUST NOT, Các bước = Steps, Format output, Chốt chặn nghiệm thu = Acceptance checkpoint are kept verbatim in Vietnamese because tools and agents parse them.)

---
name: ten-skill
description: One sentence: does what, reads what, outputs which file
---
# Skill: ten-skill
> Tuân thủ QA_STANDARD (§1 · §2 · §3 · §7 · §9 · §10)   ← point to section numbers, do not copy rules

## Mục đích                                             ← 1–3 sentences
## Đầu vào
- OUTPUT/<slug>/0N_….md
- knowledge/_project.md · knowledge/features/<slug>.md  ← always present
> Thiếu đầu vào → DỪNG (missing input → STOP)           ← never imagine
## KHÔNG được (riêng skill này)                         ← boundary with the next step
## Các bước                                             ← if a machine can do it, call a command
## Format output
# <Tên> · <slug>
Owner: … · Nguồn: … · Verdict: PASS                     ← line 2: machines read this line
| ID | … | Nguồn |                                      ← every table has a source column
## Chốt chặn nghiệm thu                                 ← a checkable checklist

Seven rules so a skill does not make the AI invent

1. Examples must be neutral

Wrong"Example: lock the account for 15 minutes after 5 failures"
Right"Example: <field> locks after <n> attempts (BR-01)"

An older version once copied voucher figures into the refund feature for exactly this reason.

2. If missing, write the label

Wrong"If absent, use a reasonable value"
Right"Not in the source ⇒ [CHƯA CÓ TRONG TÀI LIỆU – MR-xx]" (the fixed label meaning "not in the document")

3. Set no quantity targets

Wrong"Generate at least 5 questions / 20 test cases"
Right"Stop once the table is fully scanned; the quantity is decided by the documents"

4. If a machine can do it, give it to the machine

Wrong"Number BR-01, BR-02… yourself", "compute boundary points yourself"
Right"Write BR-? then run npm run ids --assign"; "copy from npm run boundary"

5. One output file, with a meta line

WrongWriting several files, or a bold verdict on line 5
RightLine 2: Owner: … · Nguồn: … · Verdict: PASS (Nguồn = source, kept verbatim: tools parse it)

6. Questions must be closed questions

Wrong"How does the system handle it?"
Right"Is the delivery date day 0 or day 1 (A/B)?"

7. A skill and a tool must not contradict each other

WrongThe skill says "do not rescan" while lint demands a rescan
RightWhen the format changes, edit lint/schema and add tests in the same pass

This bug was real, found in the refund trial run.

4

Update all 7 related places

Finishing the skill file is only half the job. The system finds and calls a skill through the 7 places below; miss one and the skill "exists but is as good as absent", or the check gate reports wrongly.

#Place to editWhat to editABC
N1skills/<name>.mdThe skill content following the templateyesyesyes
N2qa-<agent>/AGENT.mdAdd to "Skill sở hữu" (owned skills), the name matching the file name exactlyyesyes—
N3workflows/WORKFLOW.mdStage table: agent, skill, input, outputyesyesif input/output changes
N4knowledge/_system_map.jsonLookup paths (npm run map:sync)yesyes—
N5qa-lead/AGENT.mdThe coordination matrix + the phrases users commonly say to reach ityesyesif the output changes
N6tools/system/agent-doctor.jsDeclare which file the skill produces and who uses that fileif there is a new fileyes—
N7lint-deliverables.js · lib/schema.jsCheck rules + a reader for the new format, with testsif a tool reads itif a tool reads itif the format changes

A skill that produces a new output file gets the next unused sequence number in WORKFLOW.md. Do not insert in the middle, do not reuse an old number. Do not delete an old skill to "tidy up"; removal is for a human to decide.

5

Acceptance: run the commands, then run for real

a. Four commands must be green

npm testAll tool tests are green. If you edited a tool you must add new tests.
npm run agent:checkReports INTACT: every declared skill has a real file, and the places agree with each other.
npm run map:syncThe system map has the new entry.
npm run workflow -- validateNo workflow bypasses a gate.

b. Two real runs on the standard assignment set

The assignment set is in the repo at docs/skill-lab/de-bai/ (the refund feature; the scenario documents are in Vietnamese): 9 documents with planted traps including two SRS versions, comments, unapproved edits, a hidden Excel row, and a CR that changes a value. The reference results to compare against are in docs/skill-lab/01-tao-skill-moi/du-lieu/.

  1. Load the assignment into a new task: npm run intake -- docs/skill-lab/de-bai --slug <name> --force, then run the pipeline up to the stage the skill affects.
  2. Run twice, each in a fresh session, then compare: npm run diff-runs -- <run 1> <run 2>.
  3. Every difference must be explainable by a sentence in the skill. If it cannot be explained, the skill still leaves room for the AI to invent: go back to step 3.
  4. Compare with the reference results: npm run lint clean, npm run gate closing/opening at the right time, 9/9 traps still caught.
  5. Re-run an unrelated older stage to be sure the old flow still comes out as before.

c. Five conditions for a new or just-edited skill

ConditionHow to check
aPoints to rules, does not copy rulesNo verdict, label, FACT or 06W table is copied; only "QA_STANDARD §n"
bDeclares all inputs, including knowledgeHas _project.md and features/<slug>.md
cMachines can read the outputThe meta line is correct; tables have a source column; ids come from npm run ids
dTwo runs give the same resultdiff-runs, every difference explainable
eNo examples from a real projectUse only placeholders such as <field>, BR-01
6

Commit tidily, split the right parts

  • Work on a separate branch, never edit directly on develop.
  • Split into two commits: the qa-system/ edits and the trial-run data (INPUT/, OUTPUT/, knowledge/features/). Only the system-edit commit goes over to develop.
  • The pre-commit hook runs lint before every commit. Do not use --no-verify to bypass it.
  • The upgrade record (A/B/C table, the 7 places edited, command results) is kept outside the repo.

Mistakes that really happened, do not repeat them

An example turned into dataA sample knowledge file had a voucher "cap of 500.000" that was copied into the refund feature. The refund auto-approval threshold is also 500.000, so it was very easy to confuse.
The skill says one thing, the tool checks anotherSkill 02 said not to rescan, while lint demanded that a new rule have a matrix row. The AI was stuck between two rules.
Quantity targets"At least 5 questions" made every run produce a different set of questions.
Information in the wrong sectionThe success message was written only in the Happy Path section, which the checker does not read, so even a correct test case was blocked.
A dead pathA skill pointed to an agents/ folder that no longer exists, so the new skill was created where nobody reads it.
Green tests are not necessarily right331 unit tests were all green, yet running for real still exposed 8 bugs. The two-real-runs step is mandatory.

Assign a skill upgrade

Remember five things

  1. Analyze first, you approve, and only then edit.
  2. Rules live in QA_STANDARD, facts live in knowledge, a skill keeps only the method.
  3. A skill has no real examples, sets no targets, and writes a label when something is missing.
  4. Edit all 7 places; if a skill changes format, the tools change with it.
  5. Done is when the commands are green and two real runs give the same result.

Follow these five things and whatever skill you add, the system keeps running as before, and the AI still only quotes or asks, never invents.
